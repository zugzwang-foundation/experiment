01 · Verdict

Move compute from Vercel serverless to one long-lived container on ECS, and the database from Supabase to RDS for PostgreSQL 17, both in a private VPC in Mumbai. Everything else stays. The infrastructure is already written as CDK and synthesises clean.

RDS or DynamoDB?

Keep PostgreSQL. Do not move the core to DynamoDB.

One bet is one transaction across nine tables. Settling a market pays every bet atomically — DynamoDB caps a transaction at 100 items, and on an append-only ledger a half-finished settlement cannot be undone. Eleven tables are made un-editable by the database itself; DynamoDB has no such guard. And the whole database is 46 MB, roughly 87,000 rows (measured 2026-09-25) — there is no scale problem for DynamoDB to solve.

RDS is a change of address: same SQL, same guarantees, zero business-logic changes, rollback by changing one setting. DynamoDB is a rewrite of the money path during a live experiment.

04 · Why each choice, and what was rejected

Database — RDS PostgreSQL 17

Why
  • Same engine, schema, triggers and pg_cron. Zero app changes.
  • Managed backups, PITR, Multi-AZ failover.
  • Same VPC as compute — sub-millisecond queries, no pooler.
Rejected
  • DynamoDB — §06.
  • Aurora — its strengths (128 TB, replicas) address problems a 46 MB database does not have.
  • Stay on Supabase — keeps the pooler ceiling the app has been engineered around.

Compute — ECS on EC2, one long-lived task

Why
  • A persistent process whose pool timers actually run (see §07).
  • No cold starts on the bet path.
  • 30 s to drain background work on shutdown.
Rejected
  • Vercel / Lambda — ephemeral instances are the root cause of the connection problem.
  • Fargate — viable; EC2 chosen for deploy placement control. Open option.
  • EKS — a control plane for one container.

Region — ap-south-1, pinned in code

Why
  • Compute beside the data: measured 361.6 ms → 5.34 ms per query, Discovery page 35 s → 0.69 s.
Rejected
  • Inherit from AWS profile — resolved to us-east-1 on first synth. Pinned so it cannot recur.

Edge, egress, scheduling, secrets

Why
  • Cloudflare → WAF → ALB: Cloudflare already owns DNS and DDoS; ALB gives ACM certs and health checks.
  • One NAT: private container, single-task failure mode already single-AZ.
  • EventBridge for HTTP crons, rate-limited 1/sec; pg_cron stays for jobs that need row locks.
  • Secrets Manager injected at task start; Doppler stays the source of truth.
Rejected
  • CloudFront — a second CDN doubles cache invalidation.
  • Two NATs — a one-line config change if wanted.
  • Lambda for DB jobs — reimplements locking the DB already does.
  • S3 / ElastiCache — R2 and Upstash work; moving them adds risk for no gain.

One bet, end to end

Settlement is the hardest requirement: one transaction reads every position and bet in the market and writes one payout row per bet plus ledger rows per winner. All or nothing — a half-paid market is a corrupted ledger that cannot be cleaned up.

Reads are relational analytics, not lookups. Of 15 access patterns, 4 are simple key reads and 6 need joins and aggregates — the post-ranking query alone joins four tables with six aggregates, three of them COUNT(DISTINCT).

06 · Why not DynamoDB

We designed the DynamoDB table before rejecting it. It fails on five points:

#BlockerThe fact
B1No lock on the poolThe bet is a read-modify-write on the price. DynamoDB has no row lock — only optimistic conditions that collide under contention instead of queueing.
B2Settlement exceeds 100 itemsA 60-bet market is ~130 items in one atomic step. DynamoDB caps at 100. The workaround is a saga — and an append-only ledger has no undo. Disqualifying alone.
B3No triggersImmutability drops from "the database refuses" to "our code must remember".
B4No joins or aggregatesEvery aggregate becomes a hand-maintained counter inside the bet transaction. COUNT(DISTINCT) cannot be incremented — the set of ids must be stored, against a 400 KB item limit.
B5No pg_cron470 lines of in-database scheduler with row locks becomes a Lambda reimplementing locking by hand.

DynamoDB wins on operational simplicity and scale ceiling. It loses on every property this product depends on. Revisit only if the dataset grows to hundreds of gigabytes or multi-region becomes a requirement.

07 · Application

Next.js 16 · React 19 · Node 24 · Drizzle over Postgres · Better Auth. Server Components by default; route handlers for bets and uploads; every multi-write in a transaction.

The connection pool — why compute must move

One task, deliberately. maxCapacity: 1 — the Next.js cache is per-process, so a second task could serve a removed comment for the cache window. The app scales vertically until a shared cache handler exists. Adequate at this traffic; a contained follow-up, out of scope here.

Two kinds of cron. HTTP jobs (close markets every minute, drain alarms, sweep orphans) move to EventBridge — already written. In-database jobs (liquidity injector, drift check) stay in pg_cron and do not travel with a dump; they are recreated by hand and a cron-silence alarm watches them.

Failure posture. Rate limiting fails open; idempotency fails closed; moderation never blocks a post; a missing database URL fails the build rather than a deploy.

Still to do: output: 'standalone', a Dockerfile that includes drizzle/migrations/, and a health endpoint reporting the deployed commit so CI can verify the canary.

09 · How the database moves

Only the database moves; the application is pointed at a new address. Writes stop before the copy is taken and resume only after the new database has passed every check — so a bet can never land in two databases at once, which is the one outcome that cannot be repaired.

What travels with the dataWhat has to be recreated by hand
All 25 tables and their rows · the 11 append-only triggers · the 13 event-log partitions · the uuidv7() function · the migration history · the freeze timestamp The pg_cron job registrations — a dump carries the functions but not the schedule. Missing them means markets stop closing and nobody is told. Re-registered in step 4, checked in step 5, watched by the cron-silence alarm afterwards.

The migration safety guards — today they refuse to run unless the connection string contains the Supabase project id. Rewritten and tested before the window.

Step 5 — the nine checks, all must pass before the app is pointed at RDS

#CheckWhy this one
1Row counts match, table by tableAn existing tool does this and exits non-zero on mismatch
2Append-only triggers presentData without the triggers is not the same database
3A test DELETE on bets is rejectedProves the triggers are armed, not merely present
4All 13 event partitions existA missing partition loses history silently
5pg_cron jobs registered and firingOtherwise markets stop closing
6Migration history matches the codeThe health endpoint reports this directly
7The 13 invariant specs passThe four core rules, checked by machine
8Freeze timestamp preserved exactlyThe experiment's end date lives in a row
9Dharma ledger totals match, old and newThe strongest single check that nothing was lost

Why check 3 is a test and not a look. pg_restore --disable-triggers switches the append-only guards off for the load — necessary, or the data-only restore would be rejected by the very guards being preserved. If re-enabling is not verified, the database comes up with its immutability switched off and everything looks normal. A present-but-disabled trigger passes "is it there" and fails "does it reject". Run the test as the application role.

Rehearsed first. The entire window is performed on staging end to end before production is scheduled, and staging then runs on its new database under watch — the every-minute job firing, connections flat, memory steady. Rollback at any point: point DATABASE_URL back at Supabase and restart. Supabase stays alive read-only afterwards as the rollback and the reference copy.
