Database Migration Plan Supabase → AWS RDS

Moving the Database to AWS

A step-by-step plan to move Zugzwang's PostgreSQL database from Supabase to Amazon RDS while the experiment is live — rehearsed on staging first, executed in one short scheduled window, reversible at every step.

What moves
PostgreSQL only
Data size
~12,000 rows · under 1 MB
Planned downtime
20 – 30 minutes, once
Rollback
Switch one setting back

1 What moves, and what does not

Only the database moves. Everything the application talks to besides the database stays exactly where it is, so there is one thing to get right rather than seven.

📦 Moves to AWS

  • 25 tables and all their data
  • 31 migrations and the migration history
  • The append-only protections — the database rules that make bets and the reputation ledger impossible to edit or delete
  • The events table partitions
  • The scheduled database jobs: the liquidity injector and the nightly drift check
  • The project's own uuidv7() function

✅ Stays exactly where it is

  • Upstash Redis, Cloudflare R2 images, OpenAI, Resend, Sentry, PostHog
  • Sign-in — the project uses its own authentication, not Supabase's, so nothing there changes
  • File storage — images are already on Cloudflare
  • Row-level security — not used by this project, so nothing to port

Why this is smaller than it sounds

The application talks to the database as plain PostgreSQL. There is no Supabase software inside the app, so moving the database is a change of address, not a rewrite.

2 The approach, and why

One short window, not live replication

Continuously replicating from one database to the other would avoid downtime, but it is a large amount of machinery with a dangerous failure mode: a bet landing in the old database after the new one has taken over.

At this data size the copy itself takes seconds. A single scheduled window is simpler, and simpler is safer when the thing being moved is a financial-style ledger.

⚠ The risk being managed

Markets are open and people are betting. Every bet is an append-only record. The one outcome that cannot be repaired is writes landing in two databases at once.

The whole plan exists to make that impossible: writes stop, then the copy is taken, then the address changes. Never overlapping.

Recommended timing

A low-traffic window, ideally around 04:00 IST, with the operator present. Never during a seeding run, and not in the final days before the 5 November freeze.

3 Phase 1 — Build the new database (no downtime)

Done days ahead, with the live site untouched throughout.

Step 1
~2 hours

Create the RDS instance

PostgreSQL 17 in Mumbai, in the same private network as the application, reachable only from the app — never from the public internet. Automated backups and point-in-time recovery switched on from the start.

Step 2
~1 hour

Enable the scheduled-jobs extension

The liquidity injector and the nightly drift check run inside the database. RDS supports this, but it needs a custom configuration group — and the jobs themselves do not travel with the data. They are recreated by hand and verified.

Step 3
~2 hours

Update the safety guards in the code

The migration scripts today refuse to run unless the connection address contains the Supabase project identifier. Against a new database those guards would either block every migration or stop protecting the wrong one. They are rewritten to recognise the new address, reviewed, and tested — before the window, never during it.

Step 4
~1 hour

Decide how the application connects

Supabase provides a connection pooler that the app's settings were tuned against. On RDS that becomes either direct connections or RDS Proxy. The setting is chosen, applied, and then proven under the rehearsal in Phase 2 rather than assumed.

4 Phase 2 — Rehearse the whole thing on staging

This phase is not optional

Staging is a full copy of the same shape. The entire window is performed there first, end to end, and timed. That rehearsal is what turns the production window from an estimate into a known quantity — and it is the cheapest place to discover whatever we have not thought of.

What the rehearsal produces

  • A measured duration for each step, so the window is sized from evidence
  • A written command list, copy-paste ready, in order
  • Proof the verification checks in §6 actually pass on a restored copy
  • Proof the rollback works, by performing it

Then leave it running

Staging stays on its new database for at least 24 hours before production is scheduled. What we are watching for: the every-minute job still firing, database connections staying flat, memory steady, and no new errors.

Only after a clean 24 hours does the production window get a date.

5 Phase 3 — The production window, minute by minute

TimeActionWhy
T−24h Announce the window. Confirm no seeding or admin work is scheduled. Two people writing at once is the scenario this plan exists to prevent
T−1h Take a full backup of the live database and restore it somewhere to prove it is readable. An unverified backup is not a backup
T−10m Record the current row counts for every table. This is the number the new database must match exactly
T+0 Stop the application. Writes end here. The single most important moment: from now until cutover, nothing may write anywhere
T+2m Take the final copy of the database. Seconds at this size — this is the copy that becomes production
T+5m Restore it into RDS. Tables, data, protections and history together
T+10m Recreate the scheduled database jobs and confirm they are registered. They do not travel with the data; missing them stops markets closing
T+12m Run the verification checklist in §6 — all of it. The decision point: if anything fails, we stop and roll back
T+20m Point the application at the new address and start it. One setting, changed in the vault
T+22m Confirm the site reports healthy, then place one small real bet. Proves the whole write path end to end, not just that pages load
T+30m Window closes. Watch for the next two hours. Errors, connection counts, the every-minute job

Old database stays alive

Supabase is kept running, in read-only mode, for at least one week afterwards. It is the rollback, and it is also the reference copy if any number is ever disputed.

6 The verification checklist

Run against the new database before the application is pointed at it. Every line must pass; one failure stops the migration.

#CheckWhy this one
1Row counts match, table by tableThe project already has a tool that does this comparison and exits with an error on any mismatch
2The append-only protections are presentThese are what make bets and the reputation ledger un-editable. Data without them is not the same database
3A test deletion against the bets table is rejectedProves the protections are armed, not merely present
4All events partitions existA missing partition loses history silently
5The scheduled jobs are registered and fireOtherwise markets stop closing and nobody is told
6The migration history matches the codeThe health endpoint reports this directly
7The invariant test suite passes against the new databaseThe four rules the whole product rests on, checked by machine
8The freeze timestamp is preserved exactlyThe experiment's end date lives in a database row; it must survive the move untouched
9The reputation ledger totals match, old and newThe strongest single check that no row was lost in transit

7 If something goes wrong

↩ Before the switch

Nothing has changed. Start the application again on Supabase and reschedule. The only cost is the window.

↩ Just after the switch

Point the setting back at Supabase and restart. Minutes. Any bets placed in between are on the new database and are copied back before reopening.

↩ Days later

Harder, because real activity now exists only on the new database. This is why the first week is a watching week, and why the old database stays alive and readable.

Stop authority

Anyone who sees a failed check, an unexpected number, or an error on the bet path stops the migration immediately and reports it. Nobody fixes forward inside the window.

8 Timeline and what has to be in place

⏱ Realistic schedule

  • Day 1 — build the RDS instance, configure the scheduled-jobs extension
  • Day 2 — update the safety guards, review, test
  • Day 3 — full rehearsal on staging, timed and written up
  • Day 4 — staging runs on its new database, watched
  • Day 5 — the production window, in the agreed quiet hour
  • Days 5–12 — watching week, old database kept readable

📋 Needed before the window is scheduled

  • The AWS account, and agreement on instance size and backup retention
  • An agreed date and hour, with the operator present
  • Confirmation that no seeding or admin work is scheduled that day
  • A named person who can say "stop"
  • A clean rehearsal — no production window is booked before Day 3 passes

One honest note on timing

The same migration becomes markedly simpler after 5 November, when the database becomes read-only and the freeze removes the possibility of writes landing in two places at once. Doing it now is achievable and this plan is built for it — but if the date is flexible, later is safer, and the work is identical.
