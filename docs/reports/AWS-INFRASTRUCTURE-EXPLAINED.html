1 In one paragraph

Zugzwang runs on Vercel today. To move it to AWS we did not start by clicking around the AWS console. We first read the whole codebase to find everything that works only because it is on Vercel, and then wrote the AWS setup as code — ten files that describe every server, network rule, alarm and scheduled job the project needs. That code has been checked and produces a valid AWS plan, but it has not been run against AWS, and the application itself is untouched.

What actually changes

One box. The application stops being thousands of short-lived functions and becomes one always-running container, on an EC2 instance you own, next to the same database — and the three scheduled jobs move from vercel.json to EventBridge. Nothing else in the picture moves.

How writing it as code helped, concretely

🌍 Region cannot drift

AWS tooling defaults to the operator's own region. On a console setup that is invisible until the app is slow in production; here it is pinned in code and visible in a generated file before anything exists.

🔁 Ordering is proven up front

Resource ordering is checked before deployment. AWS would otherwise fail halfway through, with resources already created and a half-built environment to clean up.

🔐 Proved there are no secrets

We could scan the generated plan and show that all 31 credentials are references, not values. With a console setup there is nothing to scan.

👯 Staging matches production

Both come from the same code, so staging is a real rehearsal rather than an approximation someone assembled separately.

⏰ The crons cannot be forgotten

They are written down in the code with alarms attached, instead of living in one person's memory of what vercel.json used to do.

🔄 Rebuilding is one command

If the account is ever lost or a second region is needed, the whole setup is recreated from the repository rather than reconstructed from memory.

3 Why code instead of clicking in the console

Setting up AWS by hand looks faster on day one. It costs you later, in ways that are hard to recover from.

The tool

AWS CDK — AWS's own infrastructure-as-code tool — written in TypeScript, the same language as the rest of the project. One language for the team to maintain, not two.

5 The decisions, and the reasoning

DecisionWhy
ECS running on EC2 instancesYou own the machines — the team's preference — while ECS still schedules the container, so automatic rollback, health checks and the migration job all stay. Cheaper per month than serverless capacity; in exchange your team owns the operating system and its patching.
Region pinned to MumbaiSupabase is there. Your project already measured it: moving compute next to the database took a round trip from 361 ms to 5 ms. The wrong region throws that away.
One server, not severalNot a cost decision. Next.js caches pages inside each server, so with two servers a removed comment could stay visible on the other one. More than one needs a shared cache first.
The app's AWS identity has no permissionsIt never calls AWS — only Supabase, Upstash, R2, OpenAI, Resend, Sentry and PostHog. A future need gets added deliberately.
Passwords and keys stay out of the codeThe AWS files hold only the name of a vault entry, never a value. Doppler stays the source of truth, and rotating a key needs no deployment. We scanned the generated plan: zero secret values.
Scheduled jobs call the app with a secret headerYour cron routes already check Authorization: Bearer …, so the schedules move to AWS with no application change.
An alarm for a cron that goes quietA failing job raises an error someone can see. A job that simply stops raises nothing — markets would just never close.
30 seconds to shut downThe app finishes some work after the response is sent. Killing it instantly would drop that work.
Health check on /api/healthThe project already treats this endpoint as the truth about a deployment, so AWS uses the same signal.
Migrations run before new code servesYour existing rule (ADR-0024). If a migration fails, the old version keeps serving and nothing breaks.
Automatic rollbackA new version that fails its health checks is replaced by the previous one without waiting for a human.
NAT in production, not stagingNAT costs ~$32/month. Production gets it; staging uses a cheaper arrangement with the same inbound protection.
Firewall and CDN optionalCloudflare already fronts your domain, and two CDNs in series cause more problems than they solve. Off by default, on in one line.

Why five stacks instead of one

Each one changes for a different reason and at a different speed. The network is created once and rarely touched. The compute stack changes on every release. Alarms get tuned on their own. Splitting them means a routine deploy cannot accidentally alter the network, and a failed change rolls back only its own group.

Why the order is not written down anywhere

The tool works it out. Compute asks for the network's firewall and the security stack's identities, so those must exist first — the dependency is the reference. We originally wrote the order by hand as well, and that is exactly what produced our circular dependency; removing it fixed the problem.

The one rule that makes this testable

No stack looks anything up from a live AWS account. Everything a stack needs is passed to it as a value. That is why the whole setup can be generated and checked on a laptop, or in CI on a pull request, with no AWS credentials at all — which is how configuration risks surface before anything exists.

// bin/zugzwang.ts — the compute stack is handed what it needs
const compute = new ComputeStack(app, `${prefix}-Compute`, {
  config,
  vpc: network.vpc,             // from the network stack
  serviceSecurityGroup: network.serviceSecurityGroup,
  repository: security.repository,    // from the security stack
  appSecret: security.appSecret,
  executionRole: security.executionRole,
  logGroup: security.logGroup,
});

25 resources		 1 VPC · 4 subnets · 4 route tables + 4 routes · internet gateway · NAT gateway + its fixed IP · 2 security groups A private network split across two data centres, with a front door for visitors and a one-way exit for the app to reach Supabase, Upstash and the rest.
Security
6 resources		 1 image registry · 1 log group · 2 identities · 1 permission policy Where the app's packaged image lives, where its logs go, and the two identities: one to fetch the image and read the vault, one for the app itself — the second has no AWS permissions at all.
Compute
17 resources		 1 cluster · 2 task definitions (app + migrations) · 1 service · EC2 auto scaling group + launch template + capacity provider · instance role · load balancer + listener + target group · firewall + its attachment The running application on EC2 instances you control, the thing that receives visitors and checks the app is healthy, and a separate one-off job used to apply database migrations before a new version serves.
Scheduler
14 resources		 1 connection (holds the secret header) · 3 destinations · 3 schedules · 3 identities + 3 policies The three scheduled jobs. Each has its own identity and its own permission, so one job can never trigger another.
Monitoring
12 resources		 9 alarms · 1 notification topic · 1 dashboard Errors, slow responses, an unhealthy app, high CPU, high memory, each cron failing — and the ninth: the every-minute job going silent.

Staging is the same shape, deliberately smaller

15 network resources instead of 25 (no NAT gateway), 15 compute resources instead of 17 (no firewall), a t3.small instead of a t3.medium, and 14-day log retention instead of 90. Same code, different values — so staging genuinely rehearses production rather than resembling it.

8 How the code turns into a running system

🧪 What happens on our machines

The TypeScript is executed, and it writes out ten AWS blueprints — one per stack, per environment. Nothing is contacted, nothing is created.

pnpm typecheck  # the code compiles
pnpm synth      # 10 blueprints written to cdk.out/

This step already runs clean, and it is where configuration risks are flagged before they reach AWS.

🚀 What happens on a deploy — not yet run

AWS compares each blueprint with what exists and changes only the difference. A first deploy creates everything; a release usually changes one line — the image version.

cdk deploy 'Zugzwang-staging-*' \
  -c imageTag=staging-<commit>

The release sequence, and why the order is the whole point

Step 1

Build the image for one environment

Settings are baked in during the build, so a staging image is a staging image forever. It is tagged with the exact commit.

Step 2

Apply database migrations first

If this fails, the pipeline stops here — and the old version is still serving, untouched. That ordering is your existing rule; the pipeline enforces it rather than trusting anyone to remember.

Step 3

Start the new version alongside the old one

The load balancer sends traffic to the new version only once it answers /api/health twice in a row. The old one keeps serving until then.

Step 4

Roll back automatically if it fails

A version that never turns healthy is withdrawn by AWS on its own — no human needs to be watching.

Step 5

Verify which version is live

/api/health must report the exact commit that was just deployed, plus a healthy database and up-to-date migrations. This is the check that needs the one-line application change described in §9.

🌐 A visitor's request, once live

DNS → load balancer (HTTPS ends here) → the app container → Supabase, Upstash and R2 as needed → response. The container is reachable from the load balancer and from nothing else on the internet.

⏰ A scheduled job, once live

The schedule fires → AWS attaches the secret header from the vault → it calls the public URL, for example /api/cron/close-due-markets → your existing route checks the header and does the work. If a call fails, or stops happening at all, an alarm fires.

How secrets reach the app without ever being in the code

The code names the vault entry and the keys inside it. AWS injects the values when the container starts, so no credential is in the repository, in the blueprint, or in the image.

// lib/compute-stack.ts — names only, never values
const secrets = Object.fromEntries(
  config.secretKeys.map((key) => [
    key,
    ecs.Secret.fromSecretsManager(props.appSecret, key),
  ]),
);

We scanned the generated blueprints afterwards: 31 secrets, all of them references, zero values.

9 What the audit found — the things that would have broken

We read the application code before writing any AWS code. Five findings would have caused real incidents.

⚠ The scheduled jobs

close-due-markets runs every minute, and nothing else closes markets. Recreated on AWS, with an alarm for both failure and silence.

⚠ The deployment check would have gone blind

/api/health reports which version is live using a value only Vercel provides. On AWS it returns empty, and the check that proves the right version is live quietly stops working. Our code supplies a replacement; the app needs a one-line change to read it.

⚠ An image belongs to one environment

Some settings are baked in when the app is built, so a staging build can never be promoted to production. The deployment flow accounts for it.

⚠ A missing monitoring key crashes the app

Without one Sentry value the app refuses to start. It is now in the required list, at both build and run time.

Fifth finding

IP addresses in the logs come from a Vercel-only helper. On AWS that one log field would be empty until a small change is made. Worth knowing, not urgent.

10 What the validation step flagged

Two risks that come with AWS tooling defaults, both surfaced by generating and checking the plan. Neither would have been visible while clicking through a console — they would have appeared during a deployment, or in production.

🔁 Resource ordering

AWS refuses a setup where two groups of resources each need the other first — a normal constraint when logging, permissions and the cluster are split across groups. The check surfaced it on a laptop in seconds; on a console build it appears halfway through a deployment, with resources already created.

🌍 Region is pinned, not inherited

AWS tooling defaults to whatever region the operator's profile happens to use — us-east-1 (Virginia) here. Left at the default, the app would sit on the other side of the world from its database, undoing the single biggest performance fix this project has made. The region is now fixed in code and cannot be inherited by accident, on anyone's machine.
