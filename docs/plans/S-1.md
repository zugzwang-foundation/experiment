## Approach

Two things move, and they move independently. **The artifact** is a one-property change in
`src/db/index.ts`: the runtime reads a new `DATABASE_URL_TXN` secret instead of
`DATABASE_URL`, so the flip is visible in a diff and revertible with `git revert`. **The
demonstration** is option (e): a temporary repoint of `DATABASE_URL` in Doppler `stg` to
`:6543`, which puts the *already-deployed* staging runtime — the one running LOTS-1's
lot-minting code — into transaction mode for a scheduled window. Seven exit criteria are
observed inside that window; the eighth (criterion 1) is observed on a preview built from
this branch. Both are then rolled back, which is itself criterion 7.

## 2 · The route decision — the app reads the new secret

**Chosen: the app changes to read `DATABASE_URL_TXN`. Rejected: repointing `DATABASE_URL`
in place.** Full reasoning is in **ADR-0038 P1.1**; the three deciding facts:

1. **Blast radius.** A repoint is unscopable — it reaches the staging runtime *and* every
   open preview, because Doppler's Vercel sync has no per-secret filter.
2. **Gate C visibility.** A repoint produces a PR whose diff contains **no evidence the
   flip happened**. A reviewer cannot review a change that is not in the diff.
3. **Rollback.** `git revert` is in the repository; a dashboard edit is not.

⚠ **The third argument is weaker than it looks, and it is recorded that way.** A Doppler
change does not reach a running deployment until a redeploy — and **that holds
symmetrically for the revert**. Both rollbacks contain a redeploy, so the code route is not
meaningfully faster. **Arguments 1 and 2 carry the decision on their own.**

⚠ **This is why the demonstration and the artifact use different mechanisms.** Option (e)
*is* a repoint — the thing rejected as the shipped route — used deliberately and
temporarily, because the staging runtime deploys from the `staging` branch and cannot be
reached from this one. The repoint is reverted at the end of the window. **The merged
artifact is never a repoint.**

## 4 · How transaction mode is proven active — the observation method

**Reading `:6543` in a config file is not proof (V-3).** Neither is the app echoing its own
connection string back. The observation happens from the **DASH** side, against
`pg_stat_activity`, and it has four required properties:

1. **The observing channel must not run through the pooler under test.** Use the Supabase
   SQL editor or a direct `:5432` session — **never** Supavisor `:6543`. An observation
   multiplexed through the thing being observed cannot distinguish the subject from the
   instrument.
2. **It is a sampling loop, not a glance.** One bet is 16–19 statements and
   `pg_stat_activity` is a snapshot. A single look will miss the transaction it was opened
   to see.
3. **The control is a temporal A/B on one host.** Sample staging **before** the (e) repoint
   (on `:5432`) and **after** it (on `:6543`) — same SHA, same code, same database,
   differing in exactly one variable: pooler mode. This is what makes the difference
   attributable.
4. **Criterion 5 is established by composition, and is labelled as such.** Backend pinning
   observed at criterion 2, **plus** the static fact that all three `SET LOCAL` sites are
   transaction-scoped (`applyTxTimeouts`), gives criterion 5. That is **inference, not
   observation** — it is written down as inference, and it does not silently inherit
   criterion 2's evidence.

⚠ **No shipped HTTP surface can observe criteria 2, 5 or 6.** `pg_backend_pid` has **zero
hits repo-wide**. `/api/health` does real DB work through the shipped pool, which makes it
a clean liveness proof for criterion 1 — but it returns a boolean, opens no transaction and
reads back no GUC, **by a declared hard constraint in its own docblock**. Adding a probe
endpoint would be a file outside the declared set, i.e. a halt. **The observation is
therefore DASH-side by necessity, not by preference.**

## 5 · The rollback, as commands

**Two rollbacks, because there are two mechanisms. Both are exercised — that is criterion 7.**

**(a) The (e) repoint — the demonstration.**

```
# revert the value in Doppler stg
DATABASE_URL  :6543  ->  ...pooler.supabase.com:5432

# THEN redeploy staging — the edit alone does nothing
#   staging-provisioning.md:122 — "treat auto-redeploy as not firing"
vercel redeploy <staging-deployment> --scope <team-slug>

# verify: GET https://staging.zugzwangworld.com/api/health  ->  ok
```

**(b) The code change — the artifact.**

```
git revert <commit>          # src/db/index.ts back to DATABASE_URL
# THEN redeploy — same rule, a merge alone does not re-serve
```

⚠ **Neither rollback is complete without a deployment**, and that is the single most
important operational fact in this document. A reverted Doppler value in a dashboard, with
no redeploy, is a rollback that has not happened while looking exactly like one that has.

⚠ **Under (e), criterion 7 means two redeployments of a shared staging environment** — one
to apply, one to revert — during a window in which two other lanes are measuring against
that environment. The notification gate at the top of this document covers **both**, not
just the flip.

**Halt condition:** if the rollback does not cleanly restore, **ship nothing** until the
escape hatch works.

**The full chain is confirmed.** Criterion 4 needs, and has:

| A live session | **Confirmed** |

it reaches the transaction** — and it will present as *"the bet didn't work,"* inviting a
diagnosis of the pooler.

## 7 · `max` — the value and its derivation

**`max` stays at 4.** Derivation in **ADR-0038 P1.2**; in short:

- **The relaxation is real.** Transaction mode genuinely decouples the ceilings — client
  connections rise from 15 to 200, backend connections stay at 15. The `15 ÷ 4` sentence
  in `src/db/index.ts` is stale **as a derivation**, and is replaced this task.
- **`max` still does not move.** It bounds what a **suspended** instance can strand, not
  what a running one can use — the 2026-08-16 incident stranded a connection **idle for
  620 s** with both timers configured and verified live, because Vercel Fluid suspends
  instances and a suspended instance runs no timers. Raising `max` because the *client*
  ceiling rose recreates that incident with more sockets.
- **And ADR-0038 decision 2 forbids acting on it without measurement** — *"sizing is
  decided from measurement, never from estimate."* The relaxation says a higher `max` is
  now permissible; it does not say which value is correct. **S-5 measures; then it moves.**

**The comment edit:** the `15 ÷ 4` sentence is replaced by the stranding-risk derivation.
The value `4` is not touched. A stale comment is how the next person re-derives the wrong
number.

## What S-1 does not prove

- **`f_db`** — the fraction of a render during which a backend connection is actually held.
  Not observable from this task's declared file set and not exposed by any deployed surface.
  **S-5 must measure it; W-9 does not close without it.** (ADR-0038 P1.4.)
- **That the ceiling is cleared.** Transaction mode plus S-4's read-path reduction together
  clear it. Transaction mode alone does not, and no document here should say it does.
- **That saturation will be visible.** After the flip, overload **queues** rather than
  erroring — a load run can report "zero errors" against a fully saturated pool. The rig
  must instrument **queue depth and backend utilisation**, not error rate (**W-10**).
