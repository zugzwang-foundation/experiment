## Approach

Two things move, and they move independently. **The artifact** is a one-property change in
`src/db/index.ts`: a declared `DB_POOLER_MODE` selects which secret the runtime reads, so
the flip is visible in a diff. **The demonstration** is a **preview of this branch**, then
the **normal O-4 advance** of `main` → `staging` — with the flag set *after* the advance,
not with it (§4.3).

*Revised at Gate C. The previous version made the demonstration option (e) — a temporary
repoint of `DATABASE_URL` in Doppler `stg`, observed inside a scheduled window and then
rolled back. **Both of (e)'s justifications have since dissolved** (Tracker context), and
the advance route is strictly better on the merits, not merely on scheduling:*

- *No Doppler `stg` repoint of a live value, no shared window, no cross-lane blast radius.*
- ***The A/B is SHA-clean, and only because the flip is separated from the merge.*** *§4
  specifies a temporal A/B on one host, one variable. Under (e) that variable was a Doppler
  repoint that also hit every preview. Under a naive advance it would have been the merge
  itself — **which would have made the SHA a second variable**. Splitting the advance
  (code lands inert) from the flip (one env value) restores the single-variable guarantee
  and makes the "after" state **permanent** rather than a window. **See §4.3; the earlier
  claim that the advance route was simply "better" was an overclaim and is corrected
  there.***
- ***Criterion 7 becomes the rollback that actually matters** — `git revert` on a real
  deployment, rather than a dashboard undo.*

⚠ **S-1 ENDS WITH STAGING PERMANENTLY ON `:6543`.** Criterion 7 is *perform the rollback,
prove it works, then return to `:6543` and stay there* — **not** demonstrate-then-revert.
If S-1 ends on `:5432`, S-3 and S-5 are blocked and the task delivered nothing.

## 2 · The route decision — the app reads the new secret

**Chosen: the app changes to read `DATABASE_URL_TXN`. Rejected: repointing `DATABASE_URL`
in place.** Full reasoning is in **ADR-0038 P1.1**; the three deciding facts:

1. **Blast radius.** A repoint is unscopable — it reaches the staging runtime *and* every
   open preview, because Doppler's Vercel sync has no per-secret filter.
2. **Gate C visibility.** A repoint produces a PR whose diff contains **no evidence the
   flip happened**. A reviewer cannot review a change that is not in the diff.
3. **Rollback.** `git revert` is in the repository; a dashboard edit is not.

⚠ **The third argument is weaker than it looks, and it is recorded that way.** A Doppler
change does not reach a running deployment until a redeploy — and **that holds
symmetrically for the revert**. Both rollbacks contain a redeploy, so the code route is not
meaningfully faster. **Arguments 1 and 2 carry the decision on their own.**

⚠ **REVISED AT GATE C — the demonstration and the artifact now use the SAME mechanism, and
that is a simplification, not a compromise.** This paragraph formerly explained why they
differed: option (e) *was* a repoint — the very thing rejected as the shipped route — used
deliberately and temporarily, because the staging runtime deploys from the `staging` branch
and could not be reached from this one.

**The advance route dissolves the premise.** Reaching the staging runtime from this branch
is exactly what the O-4 `main`→`staging` advance does, so no temporary repoint is needed
and the demonstration runs on the shipped mechanism itself — the `DB_POOLER_MODE` flag plus
the committed `src/db/index.ts` change. **The thing demonstrated is now the thing shipped**,
which is strictly better evidence than demonstrating one mechanism and shipping another.

**And the original rule survives untouched: the merged artifact is never a repoint.**

### 2.1 · Where the flag lives — Doppler `stg`, unscoped

**`DB_POOLER_MODE=transaction` goes in Doppler `stg` (founder action, F-1b). No
branch-scoped Vercel variable, no transitional allow-list, no CI special case.**

*Revised at Gate C, 2026-08-22 — a reversal of the branch-scoping ruling made earlier the
same day. That ruling existed to give the flip "zero cross-team impact" and it forced
`scripts/ci-env-parity.ts` into the file set to keep the orphan check quiet. **The premise
was wrong.***

⚠ **THE FLAG IS INERT ON ANY DEPLOYMENT WHOSE CODE PREDATES IT**, and that single fact
removes the entire problem:

- Dev A (S-4-audit) and Dev C (S-2) build previews from branches cut off `main`. **`main`'s
  `src/db/index.ts` reads `DATABASE_URL` unconditionally** — there is no flag-reading logic
  in it. Their previews cannot see the variable, whatever its value.
- **Staging is the same case.** It deploys from the `staging` branch at `193d95a`, which
  *is* `main`, which also has no flag-reading code. The secret is inert there too, until the
  advance lands this branch's commit.

⇒ Setting it in Doppler `stg` today reaches **exactly one deployment: this branch's.** The
blast radius the branch-scoping was built to contain **does not exist until the merge**.

**Cross-team notification therefore happens at MERGE** — when `main` starts reading the flag
and everyone's next preview inherits it. **One message, not a gate.**

⚠ **Verified before relying on it, not assumed:** `scripts/ci-env-parity.ts` has exactly two
finding classes — *orphans* (Vercel keys with no Doppler source) and *missingRequired* (keys
absent from a Doppler config, drawn from a four-name `REQUIRED_KEYS` list). **There is no
cross-config parity check**, so a variable present in `stg` and absent from `prd` produces no
finding. `DB_POOLER_MODE` in Doppler `stg` has a Doppler source (not an orphan) and is not a
required key (not missing). **The audit stays green with no change to it.**

*The lesson recorded rather than the outcome: a mechanism was built, and a file added to the
declared set, to avoid sending one message to two people. The cost only became visible once
it was written down as a scope breach.*

### 3.1 · ⛔ Why (d) exists — the sync has no per-secret filter

**Doppler `stg` syncs to BOTH Vercel Staging and Vercel Preview, and the sync cannot be scoped
to one secret** (the D1 errata cited by ADR-0038 P1.1). This is the same property that made
option (e) unscopable, and it does not stop applying because the value being written is new
rather than repointed.

**What that means for a flag that is "inert":**

| Moment | Flag in Doppler `stg` | Staging code reads it? | Staging pooler |
|---|---|---|---|
| After (a) | `transaction` | **no** — `193d95a` has no flag logic | `:5432` |
| If (e) ran with the flag still set | `transaction` | **YES, immediately** | ⛔ **`:6543` at the same instant the code lands** |
| After (d), then (e) | *unset* | yes, but absent ⇒ `session` | ✅ `:5432` |

⛔ **Without (d), the advance IS the flip.** Sample A becomes unobtainable and the A/B collapses
back to *SHA + mode* — the exact confound §4.3 was rewritten to remove. **The inertness property
is not self-maintaining: (d) is what makes it true.**

⚠ **A merge to `main` still does not reach the staging runtime by itself** — staging deploys
from the `staging` branch (ADR-0024 decision 2), so nothing changes there until the O-4
`main`→`staging` advance happens. **What changed is who performs it: on this route the
advance is a STEP OF S-1**, not a deferred state belonging to nobody. S-1 therefore closes
with its change live on staging and staging permanently on `:6543`.

*Revised at Gate C. The previous version read "S-1 closes with its change merged and **live
nowhere**," recorded as a deferred state needing an owner. Under option (e) that was exactly
right — the (e) rollback put staging back on `:5432` and left the artifact serving nothing.
It is now false in both halves, and it sat directly beneath a banner asserting the opposite.
An executor reaching this paragraph would have found the document contradicting itself about
the one thing S-1 delivers.*

### 3.2 · The build leg — ⛔ CI DOES NOT HAVE ONE. The PREVIEW is the build leg.

**Finding about CI, recorded here because it was discovered here and is not S-1's to fix.**

Item 2 of the Gate C rulings routed the `next build` check to CI: *"open the PR as a draft
and let CI run the build leg."* **CI has no build leg.** `.github/workflows/ci.yml` runs, in
order: install → `biome check` → `tsc --noEmit` → `drizzle-kit check` → strip pg_cron →
`drizzle-kit migrate` → `db:check-drift` → `pnpm vitest run`. **There is no `next build`
step**, which also means `just verify`'s third leg is checked by *no* automated gate in this
repository. *(AGENTS.md §11 already describes CI accurately; the assumption that it built was
mine to check and I checked it.)*

⇒ **The build leg is the PREVIEW DEPLOYMENT (§3 step 2), and it is better evidence than CI
would have been.** Vercel runs `next build` with real secrets, on the platform production
runs on. A preview that deploys **is** a passed build — and criterion 1 cannot be observed
without one, so the check is already load-bearing in the sequence rather than bolted on.

⚠ **What the preview build proves, and what it does not.** It builds under the **preview**
environment, where `DB_POOLER_MODE=transaction` and `DATABASE_URL_TXN` both exist ⇒ it
proves **the transaction path builds**. It does **not** exercise the `prd` shape, where both
are absent. That case — the one that would fail the production build — is covered by the
default (`?? "session"`, so `prd` reads `DATABASE_URL` exactly as today) and pinned by the
two prod rows in `tests/unit/db/pooler-mode.test.ts`. **Three different claims, and the
evidence package keeps them apart.**

## 4 · How transaction mode is proven active — the observation method

**Reading `:6543` in a config file is not proof (V-3).** Neither is the app echoing its own
connection string back. The observation happens from the **DASH** side, against
`pg_stat_activity`, and it has four required properties:

1. **The observing channel must not run through the pooler under test.** Use the Supabase
   SQL editor or a direct `:5432` session — **never** Supavisor `:6543`. An observation
   multiplexed through the thing being observed cannot distinguish the subject from the
   instrument.
2. **It is a sampling loop, not a glance.** One bet is 16–19 statements and
   `pg_stat_activity` is a snapshot. A single look will miss the transaction it was opened
   to see.
3. **The control is a temporal A/B on one host.** Sample staging **before** the O-4 advance
   (on `:5432`) and **after** it (on `:6543`) — same host, same branch, same deploy path,
   same database. This is what makes the difference attributable.

   ✅ **THE SINGLE-VARIABLE GUARANTEE IS RECOVERED — the confound is gone, not accepted.**

   *This paragraph previously recorded a property the advance route LOST: under option (e)
   both samples ran the identical SHA, whereas an advance puts S-1's own commit into the
   "after" deployment, making **SHA a second variable**. That was correct, and the fix is
   not to accept it but to separate the two changes in time.*

   **Sample A is taken AFTER the advance and BEFORE the flag is set** (§3 steps 5-6). Both
   samples therefore run:

   | | Sample A | Sample B |
   |---|---|---|
   | SHA | the merged commit | **the same merged commit** |
   | Deployment lineage | staging | **the same staging** |
   | `DB_POOLER_MODE` | unset ⇒ `session` | `transaction` |
   | Pooler | `:5432` | `:6543` |

   **One env value moves. Nothing else does.**

   ⚠ **THIS RELIES ON A PROPERTY, AND THE PROPERTY IS BEING RELIED ON DELIBERATELY — it is
   not a happy accident.** Step 5 works only because `src/db/index.ts` defaults to
   `session` when the flag is absent, so **the merged code arrives INERT** and the advance
   carries no live behaviour change. Two things follow, and both matter more than the A/B:

   1. **The advance itself becomes safe.** A merge that changes nothing at runtime can be
      done on the ordinary O-4 schedule instead of being treated as a flip.
   2. **The flip becomes an isolated, reversible step** — one env value, not something
      riding a deploy that also carries a code change.

   ⛔ **All of this is true only while the default is `session`.** Changing that default, or
   making the flag required, silently converts the advance from an inert merge into a live
   flip and invalidates this control. **Do not change it without re-reading this section.**

   ⛔ **AND THE DEFAULT IS NOT ENOUGH ON ITS OWN — THE FLAG MUST BE UNSET BEFORE THE ADVANCE
   (§3 step d).** The paragraph above states what must be TRUE; **step (d) is what MAKES it
   true**, and the two are not the same thing.

   Doppler `stg` syncs to **both** Vercel Staging and Preview with no per-secret filter (§3.1).
   So the flag set at F-1b is live on Staging **from the moment it is written** — it is inert
   only because staging's code cannot yet read it. **The instant the advance lands flag-reading
   code, staging flips at that same instant**, sample A never exists, and the A/B collapses
   back to *SHA + mode* — the confound this whole section was rewritten to remove.

   ⚠ **This is the failure mode this section is most exposed to, because nothing goes red when
   it happens.** The advance succeeds, staging is healthy, `/api/health` reports `ok`, and the
   only casualty is a measurement nobody can take any more — an absence, which is exactly the
   kind of loss that is invisible unless it was written down in advance.
4. **Criterion 5 is established by composition, and is labelled as such.** Backend pinning
   observed at criterion 2, **plus** the static fact that all three `SET LOCAL` sites are
   transaction-scoped (`applyTxTimeouts`), gives criterion 5. That is **inference, not
   observation** — it is written down as inference, and it does not silently inherit
   criterion 2's evidence.

⚠ **No shipped HTTP surface can observe criteria 2, 5 or 6.** `pg_backend_pid` has **zero
hits repo-wide**. `/api/health` does real DB work through the shipped pool, which makes it
a clean liveness proof for criterion 1 — but it returns a boolean, opens no transaction and
reads back no GUC, **by a declared hard constraint in its own docblock**. Adding a probe
endpoint would be a file outside the declared set, i.e. a halt. **The observation is
therefore DASH-side by necessity, not by preference.**

## 5 · The rollback, as commands

**TWO ROLLBACKS AT TWO DEPTHS. Only the first is exercised; the second is documented.**

*Revised at Gate C. The original mechanism (a) was the option-(e) Doppler repoint of
`DATABASE_URL`. On the advance route the runtime state is owned by the `DB_POOLER_MODE`
flag, which makes the shallow rollback both faster and more precise — and demotes `git
revert` from "the artifact rollback" to "the deeper escape hatch."*

| Depth | Mechanism | Undoes | Exercised? |
|---|---|---|---|
| **Shallow** | unset the flag, redeploy | the **runtime state** — staging returns to `:5432` | ✅ **YES — this is criterion 7** |
| **Deep** | `git revert`, redeploy | the **code** — the flag-reading logic itself | 📄 documented, not run |

⚠ **The shallow rollback is sufficient for the runtime state, and that is the point.**
Because the default is `session` (§4.3), removing one key returns staging to exactly its
pre-S-1 behaviour **without touching the code**. `git revert` is not needed to make the
system safe; it is needed only to remove the mechanism, which is a different and rarer
decision.

**(a) The config flag — the SHALLOW rollback. THIS IS THE ONE CRITERION 7 EXERCISES.**

```
# unset the flag in Doppler stg  (absent == session mode, by design)
DB_POOLER_MODE=transaction  ->  <removed>

# THEN redeploy staging — the edit alone does nothing
```

## 6 · The positive control, and where each criterion is demonstrated

**A verification that passes when it is not looking is worth nothing (V-2).** Criterion 6
is what makes criteria 1–5 mean anything.

**The positive control:** issue a deliberately transaction-mode-incompatible statement from
the observing channel — a bare session-level `SET` (not `SET LOCAL`) followed by a read of
that GUC on a subsequent statement — and confirm it **does not persist** across the pooler's
connection reuse. If it persists, the pooler is not in transaction mode and every other
observation taken against it is void. **The control must fire before any criterion is
recorded as met.**

**It is committed as `scripts/verify-pooler-mode.ts`** and asserts **both directions** — run
against `:5432` it must report SESSION. *A probe that cannot detect the mode it is not
looking for is not a control; it is a formality that happens to agree with us.*

⚠ **It proves the POOLER, not the DEPLOYMENT.** That distinction is why the script ships and
why it is named for the measurement: it answers "is this pooler in transaction mode", which
is criterion 6, and **not** "did the deployed runtime reach that pooler", which is criterion
2 and needs the deployment. **S-5 is the named downstream caller** — it must confirm
transaction mode before load run #1, and W-10 warns that saturation goes *quiet*, so
"it looked fine" is not available as evidence.

**The criterion split — where each of the eight is demonstrated:**

the staging deployment (§3 step 6, post-flip).** The preview is what gates the PR; the
staging pass is what closes the task. A criterion met on the preview and unrepeated on

The previous version predicted `migrations: "error"` on the reasoning that `main`'s journal
head was `0024_bookmarks` while staging's database had `0025_lots` applied, so applied ⊃
journal — tolerated for previews by ADR-0024 decision 4.

**Both halves of that premise are dead.** LOTS-1 merged and staging was advanced: measured
2026-08-22, `main` = `staging` = `193d95a`, the journal head is `0026_lots_no_delete`, and
`GET /api/health` on the staging origin returns `migrations: "ok"` — which is a **per-hash
multiset compare** of the deployed code's committed migrations against
`drizzle.__drizzle_migrations` (`src/server/health/migration-drift.ts`), not a timestamp or
a count. Journal and applied now match by content hash, and this branch is rebased onto
`193d95a`.

⚠ **`"drift"` and `"error"` are DIFFERENT states and the original sentence conflated them.**
`migrationDriftStatus` returns `"drift"` when the two multisets differ, and `"error"`
**only when the comparison could not be performed at all** (database unreachable, migration
files unreadable). A journal/applied mismatch is a multiset inequality ⇒ it would have
surfaced as **`"drift"`**, never `"error"` — so the old sentence predicted a value the code
could not have produced for the reason it gave.

⇒ **Read the three outcomes as three different findings:**

| Value | Meaning here |
|---|---|
| `"ok"` | **Expected.** Journal and applied match by content hash. |
| `"drift"` | The preview is not on the rebased branch, or is bound to a different database. |
| `"error"` | The comparison could not run — DB unreachable or migration files unreadable. **Not a drift signal.** |

⛔ **This is the dangerous direction of stale, which is why it is rewritten rather than
struck.** A prediction of `"error"` left standing would have had an executor read the
**correct** result as a failure and diagnose a pooler that was working — at the exact
moment the plan existed to prevent that.

## 7 · `max` — the value and its derivation

**`max` stays at 4.** Derivation in **ADR-0038 P1.2**; in short:

- **The relaxation is real.** Transaction mode genuinely decouples the ceilings — client
  connections rise from 15 to 200, backend connections stay at 15. The `15 ÷ 4` sentence
  in `src/db/index.ts` is stale **as a derivation**, and is replaced this task.
- **`max` still does not move.** It bounds what a **suspended** instance can strand, not
  what a running one can use — the 2026-08-16 incident stranded a connection **idle for
  620 s** with both timers configured and verified live, because Vercel Fluid suspends
  instances and a suspended instance runs no timers. Raising `max` because the *client*
  ceiling rose recreates that incident with more sockets.
- **And ADR-0038 decision 2 forbids acting on it without measurement** — *"sizing is
  decided from measurement, never from estimate."* The relaxation says a higher `max` is
  now permissible; it does not say which value is correct. **S-5 measures; then it moves.**

**The comment edit:** the `15 ÷ 4` sentence is replaced by the stranding-risk derivation.
The value `4` is not touched. A stale comment is how the next person re-derives the wrong
number.

## What S-1 does not prove

- **`f_db`** — the fraction of a render during which a backend connection is actually held.
  Not observable from this task's declared file set and not exposed by any deployed surface.
  **S-5 must measure it; W-9 does not close without it.** (ADR-0038 P1.4.)
- **That the ceiling is cleared.** Transaction mode plus S-4's read-path reduction together
  clear it. Transaction mode alone does not, and no document here should say it does.
- **That saturation will be visible.** After the flip, overload **queues** rather than

  must instrument **queue depth and backend utilisation**, not error rate (**W-10**).
