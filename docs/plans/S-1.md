## Approach

Two things move, and they move independently. **The artifact** is a one-property change in
`src/db/index.ts`: a declared `DB_POOLER_MODE` selects which secret the runtime reads, so
the flip is visible in a diff and revertible with `git revert`. **The demonstration** is a
**branch-scoped preview**, then the **normal O-4 advance** of `main` → `staging`.

*Revised at Gate C. The previous version made the demonstration option (e) — a temporary
repoint of `DATABASE_URL` in Doppler `stg`, observed inside a scheduled window and then
rolled back. **Both of (e)'s justifications have since dissolved** (Tracker context), and
the advance route is strictly better on the merits, not merely on scheduling:*

- *No Doppler `stg` repoint, no shared window, no cross-lane blast radius.*
- ***The §4 A/B gets BETTER.** §4 specifies a temporal A/B on one host, same SHA, one
  variable. Under (e) that variable was a Doppler repoint that also hit every preview.
  Under the advance it is **staging-before-advance vs staging-after-advance** — same deploy
  path, same branch, one variable — and the "after" state is **permanent** rather than a
  window.*
- ***Criterion 7 becomes the rollback that actually matters** — `git revert` on a real
  deployment, rather than a dashboard undo.*

⚠ **S-1 ENDS WITH STAGING PERMANENTLY ON `:6543`.** Criterion 7 is *perform the rollback,
prove it works, then return to `:6543` and stay there* — **not** demonstrate-then-revert.
If S-1 ends on `:5432`, S-3 and S-5 are blocked and the task delivered nothing.

## 2 · The route decision — the app reads the new secret

**Chosen: the app changes to read `DATABASE_URL_TXN`. Rejected: repointing `DATABASE_URL`
in place.** Full reasoning is in **ADR-0038 P1.1**; the three deciding facts:

1. **Blast radius.** A repoint is unscopable — it reaches the staging runtime *and* every
   open preview, because Doppler's Vercel sync has no per-secret filter.
2. **Gate C visibility.** A repoint produces a PR whose diff contains **no evidence the
   flip happened**. A reviewer cannot review a change that is not in the diff.
3. **Rollback.** `git revert` is in the repository; a dashboard edit is not.

⚠ **The third argument is weaker than it looks, and it is recorded that way.** A Doppler
change does not reach a running deployment until a redeploy — and **that holds
symmetrically for the revert**. Both rollbacks contain a redeploy, so the code route is not
meaningfully faster. **Arguments 1 and 2 carry the decision on their own.**

⚠ **REVISED AT GATE C — the demonstration and the artifact now use the SAME mechanism, and
that is a simplification, not a compromise.** This paragraph formerly explained why they
differed: option (e) *was* a repoint — the very thing rejected as the shipped route — used
deliberately and temporarily, because the staging runtime deploys from the `staging` branch
and could not be reached from this one.

**The advance route dissolves the premise.** Reaching the staging runtime from this branch
is exactly what the O-4 `main`→`staging` advance does, so no temporary repoint is needed
and the demonstration runs on the shipped mechanism itself — the `DB_POOLER_MODE` flag plus
the committed `src/db/index.ts` change. **The thing demonstrated is now the thing shipped**,
which is strictly better evidence than demonstrating one mechanism and shipping another.

**And the original rule survives untouched: the merged artifact is never a repoint.**

## 4 · How transaction mode is proven active — the observation method

**Reading `:6543` in a config file is not proof (V-3).** Neither is the app echoing its own
connection string back. The observation happens from the **DASH** side, against
`pg_stat_activity`, and it has four required properties:

1. **The observing channel must not run through the pooler under test.** Use the Supabase
   SQL editor or a direct `:5432` session — **never** Supavisor `:6543`. An observation
   multiplexed through the thing being observed cannot distinguish the subject from the
   instrument.
2. **It is a sampling loop, not a glance.** One bet is 16–19 statements and
   `pg_stat_activity` is a snapshot. A single look will miss the transaction it was opened
   to see.
3. **The control is a temporal A/B on one host.** Sample staging **before** the O-4 advance
   (on `:5432`) and **after** it (on `:6543`) — same host, same branch, same deploy path,
   same database. This is what makes the difference attributable.

   ⚠ **One property of the (e) control is LOST here, and it is not a wash.** Under (e) the
   two samples ran the **identical SHA** and differed only in a Doppler value. Under the
   advance they cannot: the "after" deployment necessarily carries S-1's own commit, so
   **SHA is a second variable**. The A/B is still sound — the only runtime-affecting delta
   in that commit is `src/db/index.ts`'s mode selection, the rest being docs and tests —
   but that is an argument from the diff's content, **not** the clean single-variable
   guarantee (e) had. State it in the evidence as such. *(The Gate C reply said the A/B
   "gets better"; it gets better on permanence and blast radius, and worse on this. Both
   are true and the record should carry both.)*
4. **Criterion 5 is established by composition, and is labelled as such.** Backend pinning
   observed at criterion 2, **plus** the static fact that all three `SET LOCAL` sites are
   transaction-scoped (`applyTxTimeouts`), gives criterion 5. That is **inference, not
   observation** — it is written down as inference, and it does not silently inherit
   criterion 2's evidence.

⚠ **No shipped HTTP surface can observe criteria 2, 5 or 6.** `pg_backend_pid` has **zero
hits repo-wide**. `/api/health` does real DB work through the shipped pool, which makes it
a clean liveness proof for criterion 1 — but it returns a boolean, opens no transaction and
reads back no GUC, **by a declared hard constraint in its own docblock**. Adding a probe
endpoint would be a file outside the declared set, i.e. a halt. **The observation is
therefore DASH-side by necessity, not by preference.**

## 5 · The rollback, as commands

**Two rollbacks, because there are still two mechanisms. Both are exercised — that is
criterion 7.** *Revised at Gate C: mechanism (a) was the option-(e) Doppler repoint of
`DATABASE_URL`. On the advance route the config mechanism is the `DB_POOLER_MODE` flag
instead, and mechanism (b) is unchanged.*

**(a) The config flag — the FAST rollback.**

```
# unset the flag in Doppler stg  (absent == session mode, by design)
DB_POOLER_MODE=transaction  ->  <removed>

# THEN redeploy staging — the edit alone does nothing
#   staging-provisioning.md:122 — "treat auto-redeploy as not firing"
vercel redeploy <staging-deployment> --scope <team-slug>

# verify: GET https://staging.zugzwangworld.com/api/health  ->  ok
```

⚠ **This is a property worth naming, because it was designed in rather than found.** The
default is `session` (`src/db/index.ts`), so **removing one key is a complete rollback** —
`DATABASE_URL_TXN` can stay minted, and nothing else has to move. The shape that was
rejected, `DATABASE_URL_TXN ?? DATABASE_URL`, would have made this same act
indistinguishable from a missing secret.

**(b) The code change — the artifact.**

```
git revert <commit>          # src/db/index.ts back to reading DATABASE_URL only
# THEN redeploy — same rule, a merge alone does not re-serve
```

⚠ **Neither rollback is complete without a deployment**, and that is the single most
important operational fact in this document. A reverted Doppler value in a dashboard, with
no redeploy, is a rollback that has not happened while looking exactly like one that has.

⚠ **Criterion 7 is NOT demonstrate-then-revert.** It is *perform the rollback, prove it
restores, then return to `:6543` and stay there.* **If S-1 ends on `:5432`, S-3 and S-5 are
blocked and the task delivered nothing.** *Revised at Gate C: the previous version warned
that criterion 7 meant two redeployments of a shared environment during a window two other
lanes were measuring against. The advance route removes the window and the cross-lane
exposure — previews inheriting the flag is now intended — so what remains is the ordinary
cost of a redeploy, and the standing rule that staging finishes on `:6543`.*

**Halt condition:** if the rollback does not cleanly restore, **ship nothing** until the
escape hatch works.

⚠ **`"drift"` and `"error"` are DIFFERENT states and the original sentence conflated them.**

| Value | Meaning here |
|---|---|
| `"ok"` | **Expected.** Journal and applied match by content hash. |
| `"drift"` | The preview is not on the rebased branch, or is bound to a different database. |
| `"error"` | The comparison could not run — DB unreachable or migration files unreadable. **Not a drift signal.** |

struck.** A prediction of `"error"` left standing would have had an executor read the

## 7 · `max` — the value and its derivation

**`max` stays at 4.** Derivation in **ADR-0038 P1.2**; in short:

- **The relaxation is real.** Transaction mode genuinely decouples the ceilings — client
  connections rise from 15 to 200, backend connections stay at 15. The `15 ÷ 4` sentence
  in `src/db/index.ts` is stale **as a derivation**, and is replaced this task.
- **`max` still does not move.** It bounds what a **suspended** instance can strand, not
  what a running one can use — the 2026-08-16 incident stranded a connection **idle for
  620 s** with both timers configured and verified live, because Vercel Fluid suspends
  instances and a suspended instance runs no timers. Raising `max` because the *client*
  ceiling rose recreates that incident with more sockets.
- **And ADR-0038 decision 2 forbids acting on it without measurement** — *"sizing is
  decided from measurement, never from estimate."* The relaxation says a higher `max` is
  now permissible; it does not say which value is correct. **S-5 measures; then it moves.**

**The comment edit:** the `15 ÷ 4` sentence is replaced by the stranding-risk derivation.
The value `4` is not touched. A stale comment is how the next person re-derives the wrong
number.

  **S-5 must measure it; W-9 does not close without it.** (ADR-0038 P1.4.)
- **That the ceiling is cleared.** Transaction mode plus S-4's read-path reduction together
  clear it. Transaction mode alone does not, and no document here should say it does.
- **That saturation will be visible.** After the flip, overload **queues** rather than
  erroring — a load run can report "zero errors" against a fully saturated pool. The rig
  must instrument **queue depth and backend utilisation**, not error rate (**W-10**).
