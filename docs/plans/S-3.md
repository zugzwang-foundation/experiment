## Context

Google OAuth signup nests two connection checkouts inside one 4-slot pool, and nothing on either side ends the standoff.

`createOAuthUser` (`internal-adapter.mjs:57`) wraps its user-INSERT and account-INSERT in `runWithTransaction`, which is a real `db.transaction` because `transaction: true` is set at `auth/index.ts:335`. One connection is held for the duration. Inside it, `databaseHooks.user.create.before` (`:450`) calls `consumeIdentityPoolTuple(db)` at `:451` against the **module-level `db`**, not the transaction handle, and `consume.ts:28` opens its own `db.transaction` — a **second** connection from the same pool.

`src/db/index.ts:96` sets `max: 4`. Four concurrent OAuth signups each hold one slot and each wait for a second; postgres.js has no acquire timeout. Measured on staging: `idle_in_transaction_session_timeout = 0` and `idle_session_timeout = 0` — both reapers **off**; `statement_timeout = 120s` never arms because a backend idle inside an open transaction runs no statement; `maxDuration` is unset repo-wide.

The Google callback carries no rate limit of ours (`auth/index.ts:136-139` excludes it). **Four unauthenticated requests wedge an instance, and that instance then fails every route it serves.** This is an availability defect, not a throughput one.

Email-OTP signup is unaffected: `createUser` (`:75`) is a bare `createWithHooks` and opens no transaction at any layer.

**Why it hid.** `transaction: true` is a **capability**, not a **state**. It populates `adapter.transaction` (`core/factory.mjs:402-408`, default `false` at `:29`) and changes nothing for any path that never invokes it. Reading the flag and inferring behaviour put this on the wrong door for five days.

## Q-P1 — closed from source. **YES.**

**Question.** Does `findOAuthUser` fall back to an email lookup, and link the account, when no `(providerId, accountId)` row matches?

### Part 1 — the fallback is unconditional

`node_modules/better-auth/dist/db/internal-adapter.mjs:440-460` (better-auth `1.6.11`), the `else` arm taken when the account lookup returns nothing:

```js
			else {
				const user = await (await getCurrentAdapter(adapter)).findOne({
					model: "user",
					where: [{ value: email.toLowerCase(), field: "email" }]
				});
				if (user) return {
					user,
					linkedAccount: null,
					accounts: await (await getCurrentAdapter(adapter)).findMany({
						model: "account",
						where: [{ value: user.id, field: "userId" }]
					}) || []
				};
				else return null;
			}
```

**No gate of any kind.** The email arm is not conditioned on `accountLinking`, on a flag, or on anything else.

### Part 2 — the caller links, and does so with `accountLinking` ABSENT

`findOAuthUser` only finds; it returns `linkedAccount: null`. Linking is decided at `oauth2/link-account.mjs:17-30`. `&&` binds tighter than `||`, so the gate at `:22` is four disjuncts:

| # | Disjunct | Value | Established by | Can it drift from our side? |
|---|---|---|---|---|
| 1 | `!isTrustedProvider && !userInfo.emailVerified` | **false** | `@better-auth/core/.../google.mjs:92-93` is `emailVerified: user.email_verified, ...userMap` — spread **last**, so `mapProfileToUser`'s `emailVerified: true` (`auth/index.ts:420`) overrides it, and `:411-415` throws `oauth_email_not_verified` otherwise | vendor constant vs. absent config — **no** |
| 2 | `requireLocalEmailVerified && !dbUser.user.emailVerified` | **false** | `undefined ?? true = true`, so this turns entirely on the **stored** `users.email_verified` | ⛔ **YES — this is the fragile one** |
| 3 | `accountLinking?.enabled === false` | **false** | `undefined === false` | **no** |
| 4 | `accountLinking?.disableImplicitLinking === true` | **false** | `undefined === true` | **no** |

All four false ⇒ no early return ⇒ `linkAccount()` runs ⇒ **the orphan self-heals on the next sign-in.**

`grep` over `src/server/auth/index.ts` for `account:` / `accountLinking` / `trustedProviders` / `disableImplicitLinking` / `requireLocalEmailVerified` returns **zero hits**, so `c.context.options.account` is `undefined`.

**Row 1 — "Yes."** Explicitly **not** row 3: linking happens with `accountLinking` **absent**, i.e. by vendor default. The gate blocks only when `accountLinking.enabled === false` is *explicitly set*. **Nothing is enabled, no configuration is added, and the auth surface is not widened.**

### Why disjunct 2 gets a test and the other three do not (A-5 §4)

Disjunct 2 is the only one that depends on code we write. Its inputs:

- `src/db/schema/auth.ts:37` — `emailVerified: boolean("email_verified").notNull().default(false)`. **The column default is the lockout value.** A row that lands `false` fails disjunct 2 forever and does not error while doing it.
- `user.create.before` (`auth/index.ts:457-462`) returns `{ data: { ...user, pseudonym, pfpFilename } }` — spreads `user`, does not touch `emailVerified`.
- `emailVerified` is one of Better Auth's **6 core** user-model fields, so the `transformInput` stripping that caused FIX-AUTH-SIGNUP (`factory.mjs:108-109`) does not reach it.

Every hop holds. **They are still three hops**, and v2 inferred across all three — exactly the shape of reasoning that put this defect on the wrong door for five days.

Disjuncts 1, 3 and 4 reduce to **vendor constants against an absent config**. They cannot drift from our side. **Record them in ADR-0042 with the quoted table above; do not build test scaffolding to observe a constant.**

## Constraints

### C-1 · N derives from the shipped `max`, guarded by a BOUND not an equality (A-6)

`N = max`. A nested-checkout deadlock triggers at exactly `max` concurrent **whatever `max` is** — the structure is max-independent, so `N = POOL_MAX` self-calibrates and an equality guard would only schedule a CI break on the day S-5 raises it.

```ts
import { db } from "@/db";

// Calibration: first measured at max: 4 (S-3, 2026-08-27).
// N self-calibrates — a nested-checkout deadlock fires at exactly `max`,
// whatever max is. The bound below is a practicality limit, not a
// correctness one: above 16 this test fires more than sixteen concurrent
// signups on every CI run and has become impractical rather than merely
// recalibrated.
const POOL_MAX = db.$client.options.max;   // typed, no cast
if (POOL_MAX > 16) {
  throw new Error(
    `S-3 demonstration fires POOL_MAX concurrent signups; src/db/index.ts now reports ` +
    `max: ${POOL_MAX}, above the practical ceiling of 16. Re-scope the demonstration ` +
    `before trusting it. See docs/adr/0042.`,
  );
}
const N = POOL_MAX;
```

`drizzle-orm/postgres-js/driver.d.ts:23` exposes `$client: TClient`; postgres.js types `max: number` on `BaseOptions` (`postgres/types/index.d.ts:52`), reached via `options: ParsedOptions` (`:706`). **A loud throw, not a `console.warn`** — O-1.

⚠ **This is not a new AGENTS.md §7 exception.** That rule governs *scripts under `tsx`*. Tests reach `@/db` through the `server-only` alias shim (`vitest.config.ts:24-27`), and `signup-create-path.integration.test.ts` already imports `@/server/auth/index` → `@/db` today. No second exception is created.

### C-2 · `pg_stat_activity` — one assertion shape, two expected values (A-4)

**⛔ A-4 corrected a defect that would have failed step 6 on a correct fix.** v2 asserted zero backends `idle in transaction` post-fix. **Candidate A removes one transaction, not every transaction.** `consumeIdentityPoolTuple` calls `db.transaction()` directly at `consume.ts:28` and **survives the fix byte for byte**; it runs `SELECT … FOR UPDATE SKIP LOCKED` then `UPDATE` with a client round-trip between, and for that round-trip the backend holds an open transaction running no query — which is exactly `state = 'idle in transaction'`. Taking the maximum across samples *maximises* the chance of catching one. Step 6 would have gone red on a working fix, at the exit criterion, where it is most expensive.

**The discriminator is not presence. It is PERSISTENCE.**

- **Pre-fix:** the same N backends hold open transactions waiting for a connection that never comes. The same `pid`s appear in **every** sample, indefinitely.
- **Post-fix:** `consume.ts`'s transactions open and close. `pid`s churn. No `pid` survives the whole window.

#### The assertion — intersection, in both directions

Collect the **set of `pid`s per sample**, not a count. Then:

| Run | Assertion | Says |
|---|---|---|
| Pre-fix | max per-sample count `=== N` | V-2 attribution: a hang alone is consistent with a slow DB; N backends `idle in transaction` is not |
| Pre-fix | **intersection across all samples, `size === N`** | the same N backends, never moving — a wedge |
| Post-fix | **intersection across all samples, `size === 0`** | every transaction opened and closed — churn, not a wedge |

**One assertion shape, two expected values.** The pre-fix count assertion is retained alongside it (ratification §7 keeps it standing); the two say different things and both are cheap.

#### ⛔ The sample rule — three samples TAKEN, not three containing rows

**Post-fix, most samples will legitimately be empty. That is the point of A-4.** Requiring three *non-empty* samples would make a correct fix unprovable.

- **Require ≥ 3 samples TAKEN** across the window. An intersection over one sample is trivially itself and proves nothing; over zero samples it is vacuous. Fewer than three ⇒ **inconclusive, fail the run.**
- **Prove overlap SEPARATELY.** In the same poll, also select `state IN ('active','idle in transaction')` and require **≥ 1 sample with rows** — that is what establishes the observation window actually overlapped live work. Without it, a post-fix empty intersection could just mean the burst finished before polling began.
- **The assertion itself stays scoped to `state = 'idle in transaction'`.** The `active` rows are the overlap witness only; they never enter the intersection.

```sql
SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start AS in_xact,
       left(query, 120) AS last_query
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid()
  AND state IN ('active', 'idle in transaction')
```

**The observation channel is genuinely separate.** `tests/db/_fixtures/db.ts:31-32` constructs `testClient` and `drizzleClient` as two `postgres(connectionString, { max: 1 })` handles — **distinct pools from `@/db`'s**. `testClient` still answers while the application pool is wedged.

#### The mechanism — four steps, unchanged from v2, all ratified

1. **Fire the N calls and DO NOT await them yet.** Collect the promises. Awaiting `Promise.all` before observing never runs pre-fix, and post-fix reads an empty set for the wrong reason.
2. **Poll, never a single bare sleep.** Short interval, bounded deadline, accumulating a `Set<number>` of pids per sample.
3. **Overlap the observation with live work** — start polling, then `await Promise.all(inflight)` in the same test, and assert on the accumulated samples.
4. **`Promise.allSettled` on `inflight` in a `finally`**, so a pre-fix wedge cannot strand unhandled rejections when the test times out.

⚠ **Write the reason into the test docblock.** The next reader will ask why a transaction still exists after a change whose entire purpose was to remove one — and `consume.ts:19-23`'s comment, which is wrong (`S3-8`), is what they will find first.

### C-3 · Teardown must be bounded

**`client.end({ timeout: N })`, never bare `end()`.** postgres.js `end()` defers until in-flight queries complete (`src/db/index.ts:130-132`, the repo's own words), which on a wedged pool is **never**. A bare `end()` in `afterAll` converts a clean red into a hung runner. Use `{ timeout: 5 }` on every client the file opens.

### C-3a · The pre-flight reads the SHIPPED host, not `process.env`

`src/db/index.ts` selects between `DATABASE_URL` and `DATABASE_URL_TXN` on `DB_POOLER_MODE` (`:45`, `:65-66`, feeding the single `postgres(...)` at `:74`). A pre-flight reading `DATABASE_URL` can certify one endpoint while the pool connected on the other. **Session mode makes them identical today — a coincidence of configuration, not a property**, and S-1 shipped the machinery to end it.

`postgres/types/index.d.ts:378-382` — `ParsedOptions` **narrows** `BaseOptions`' `host: string | string[] | undefined` to `host: string[]` and `port` to `number[]`, because postgres.js supports a multi-host failover list:

```ts
  interface ParsedOptions<T extends Record<string, unknown> = {}> extends BaseOptions<…> {
    /** @inheritdoc */
    host: string[];
    /** @inheritdoc */
    port: number[];
```

```ts
const LOOPBACK = new Set(["localhost", "127.0.0.1", "::1"]);
const hosts = db.$client.options.host;   // string[] — typed, no cast
if (hosts.length === 0 || !hosts.every((h) => LOOPBACK.has(h))) {
  throw new Error(
    `S-3 demonstration refuses to run against non-loopback host(s): ${hosts.join(", ")}. ` +
    `It fires db.$client.options.max concurrent signups and wedges the pool by design.`,
  );
}
```

⚠ **`every`, not `[0]`** — one non-loopback element in a failover list is reachable on a retry the pre-flight never inspected.

This throws **before a single row is written**, and it is the only thing between a stale developer config and N concurrent signups fired at staging.
