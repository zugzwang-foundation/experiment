---

# 1. Frontend Mission

Prove how the user-facing website behaves under realistic concurrent read and mixed traffic, and identify frontend request amplification or rendering bottlenecks that propagate into the backend/cache/DB layers.

The frontend work must answer:

- Which pages consume the most backend work?
- Which pages create request waterfalls?
- How does the 15-second polling path amplify traffic?
- Does cache effectiveness degrade as writes increase?
- What is the cold-start cost?
- How much work happens on server render vs client hydration?
- Which page-level bottlenecks are real and which are only hypotheses?

# 5. Frontend Measurement Model

## Page-level metrics

For each important page:

- total request duration
- p50
- p90
- p95
- p99
- response size
- request count per page view
- downstream API count
- errors/timeouts
- cold vs warm

## Request-amplification metrics

Measure:

```text
1 page view
→ N HTTP requests
→ M cache operations
→ K DB-dependent operations
```

The exact amplification factor must come from observed data, not assumptions.

## Polling metrics

Measure:

- request frequency
- layout re-execution
- page refresh cost
- requests while tab visible
- requests while tab hidden, where the test profile covers it
- backend load generated by polling

## Cache metrics

Measure where observability exists:

- warm/cold behavior
- cache hit/miss
- invalidation effect
- latency hit vs miss
- write-triggered cache churn

Do not label the cache a bottleneck merely because a cache exists.

# 6. Frontend Test Profiles

## Profile A — Read-only audience

Purpose:

- measure normal browsing
- isolate frontend read amplification
- establish page-level latency

Traffic:

- homepage
- market pages
- user pages
- quote/export where approved

## Profile B — Mixed 90/10

Use the ratified mixed profile:

- ~90% audience/read
- ~10% bettor/write

Frontend objective:

- measure read performance while backend writes invalidate/refresh cached data
- observe polling under concurrent writes
- correlate page latency with backend queue/cache effects

## Profile C — Cold-start

Start from an approved idle/cold condition.

Record:

- first-request latency
- subsequent warm latency
- discovery-specific cold cost

Do not compare an uncontrolled one-off cold request directly with a controlled cold-start experiment.

## Profile D — Polling amplification

Target `/m/[slug]` and its 15-second polling path.

Measure:

- requests per interval
- layout/page work
- cache activity
- backend requests
- effect of visibility suspension

## Profile E — Hot market read

Many readers on the same market while writes arrive.

Purpose:

- expose cache invalidation amplification
- expose expensive market reads
- test participant/reserve-keyed cache behavior

# 8. Frontend Cache Test Plan

Current architecture may involve:

```text
Browser
  ↓
CDN / Vercel
  ↓
Next Data Cache
  ↓
"use cache"
  ↓
React.cache
  ↓
Upstash
  ↓
Postgres
```

For each important surface, record:

- cache key
- TTL/revalidation behavior
- invalidation trigger
- cache hit/miss observability
- cold path
- failure behavior

### Critical frontend cache questions

1. Does a write invalidate the cache for all readers?
2. Does the cache key change often enough to cause misses under activity?
3. Does a cold miss amplify DB traffic?
4. Does the star-count cache degrade silently?
5. Does the presigned-URL/cache lifetime relationship remain valid at expiry?
6. Does cache invalidation latency exceed the user-visible freshness requirement?

No new cache technology should be introduced solely because it is common industry practice. Measure first.

---

# 9. Frontend k6 Workload Design

k6 is HTTP-level, not a full browser automation framework. Therefore explicitly separate:

### HTTP page/load testing

Good for:

- page response latency
- API latency
- request rates
- concurrency
- backend propagation

### Real-browser validation

Use only if the project later authorizes a browser-level tool for:

- hydration
- JavaScript execution
- paint timing
- interaction timing
- true browser cache behavior

Do not claim a k6 HTTP test proves browser rendering performance that it does not execute.

Focus on:

- cache invalidation

## FE-4 — Polling Storm

Use the approved 15-second polling model.

Compare:

- visible tab behavior
- hidden tab behavior where applicable
- normal market vs hot market

## FE-5 — Cold Start

Run from controlled idle state.

Compare:

```text
Cold request
vs
Warm request
```

## FE-6 — Hot Market

Concentrate many readers on a single market while writes land.

## FE-7 — Spike

Ramp page traffic sharply.

Measure recovery.

## FE-8 — Soak

Sustain moderate read/mixed traffic.

Observe:

- latency drift
- memory/resource drift
- cache degradation
- polling amplification over time

## FE-9 — Correlation / Capacity

Correlate page degradation with backend/cache/DB evidence.

Do not call the frontend the bottleneck unless its own measurements support the conclusion.

# 11. Frontend Bottleneck Decision Tree

```text
Page p95/p99 ↑
      │
      ├─ Request count/page ↑ ?
      │      └─ YES → request amplification
      │
      ├─ One request dominates?
      │      └─ YES → endpoint/backend investigation
      │
      ├─ Cache miss ↑ ?
      │      └─ YES → cache/invalidation investigation
      │
      ├─ Discovery sequential depth visible?
      │      └─ YES → frontend/backend fan-out investigation
      │
      ├─ Polling interval creates repeated layout work?
      │      └─ YES → polling amplification
      │
      ├─ Cold only?
      │      └─ YES → cold-start investigation
      │
      └─ Browser-only symptom?
             └─ YES → browser-level test required
```

# 13. Frontend Correctness Checks

Load testing must not create user-visible correctness failures.

Verify:

- correct market values
- correct user data
- no stale critical state beyond approved window
- correct freeze/read behavior
- no broken polling loop
- no duplicate actions caused by refresh
- no missing content due to cache failure
- no asset URL expiry regression

A faster page that shows incorrect state is a failed result.

# 16. Frontend Optimization Process

Do not optimize from intuition alone.

Use:

```text
Measure
  ↓
Identify amplification / bottleneck
  ↓
Make one approved change
  ↓
Repeat identical test
  ↓
Compare
```

Possible future optimization categories, only when measurement supports them:

- parallelizing safe independent work
- bounding unbounded reads
- reducing unnecessary refresh/layout work
- improving cache-key/invalidation strategy
- reducing request amplification
- reducing payload size
- reducing client-side JavaScript
- image/font optimization
- browser-level optimization

# 19. Frontend–Backend Handoff Contract

Whenever a frontend test exposes a backend-looking bottleneck, the frontend developer must hand off:

```text
Page / surface
↓
Request that dominates
↓
Observed latency
↓
Request amplification
↓
Cache state
↓
Backend queue / utilisation evidence
↓
Relevant timestamp/run ID
```

The backend developer then determines whether the root cause is:

- API
- pool
- DB
- cache
- external service
- infrastructure

Likewise, backend write tests must return:

- write arrival profile
- affected page/cache path
- invalidation events
- timestamp/run ID

so the frontend developer can measure user-facing impact.

# 20. Final Frontend Capacity Result

The final report must distinguish:

### Measured
What the test directly observed.

### Correlated
What backend/cache evidence supports.

### Hypothesis
What remains unproven.

### Recommended
What should be changed after approval.

Do not declare “frontend ready for 5K users” unless the approved target, workload, pass/fail criteria, and evidence all support that statement.
