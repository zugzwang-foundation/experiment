## Per-bottleneck detail — the P0/P1 set

Format per the brief: *Evidence · Why it matters · How to measure · Expected symptom ·
Potential optimization · How to validate.*

### BR-1 · Unbounded request wall clock
- **Evidence.** Two greps returning zero, plus ADR-0038 P1's own paragraph: *"Under saturation a bet now hangs for an unknown, Supavisor-side `pool_checkout_timeout` that is not configured, recorded, or measured anywhere in this repo."*
- **Why it matters.** ⛔ A hang is **not a failure mode the bet path previously had**, so no halt condition, alarm or runbook names it. Under `:5432` exhaustion failed immediately and loudly with `EMAXCONNSESSION`.
- **How to measure.** Rig-side per-request wall clock; `pg_stat_activity` sampling for the correlated backend state; the Supavisor `pool_checkout_timeout` value read from the dashboard (it is not in this repo).
- **Expected symptom.** A long tail with no error class attached; p99 detached from p95.
- **Potential optimization.** A route-level or `vercel.json` `maxDuration` on the money path.
- **How to validate.** A saturation run before and after: the tail must terminate in a *classified error* rather than a hang, with the invariant suite green on the corpus either way.

### BR-5 · `max: 4` and the stranding question
- **Evidence.** S-3's reproduction (deadlock at N=4, clean at N=3 — a **positive control**, which is what makes it evidence rather than an anecdote); the `src/db/index.ts` docblock; ADR-0038 P1.2.
- **Why it matters.** It is the one number with a demonstrated failure behind it, and ADR-0038 decision 2 reserves the move to a measurement that does not yet exist.
- **How to measure.** Concurrent-signup ceiling at `max ∈ {4, 8, 16}` — **and the pool state after the load stops**, which is a different observation window and the easy one to omit.
- **Expected symptom.** Throughput plateaus; separately, connections persist long past both timers because a suspended Fluid instance runs none (620 s observed against a 20 s setting).
- **Potential optimization.** A measured `max`.
- **How to validate.** ⛔ **Not here.** Moving the literal is a code change on a fenced file needing its own task, ADR and ritual. S-5 outputs a recommended value **with the measurement behind it**.

### BR-7 · Activity-coupled cache invalidation
- **Evidence.** ADR-0041 D-2 (the key is the full received argument list, verified from the compiled build); the `cached-view.ts` docblock, which names the failure *"invalidation coupled to activity performs worst when load is highest"* — and then fixes it **only for the chart**.
- **Why it matters.** It converts the read-path collapse from a constant win into one that decays exactly under the ratified 90/10 mixed profile.
- **How to measure.** Hit rate segmented by market write-rate, during Stage 4. A single-user warm number (S-4's) cannot see this.
- **Expected symptom.** Discovery and `/m/[slug]` p95 rising with **write** rate, not read rate.
- **Potential optimization.** The `getCachedReserveWalk` shape — a market-id-keyed inner cache with a time floor — applied to the comment read.
- **How to validate.** Re-run Stage 4 and compare hit rate at the same write rate; and re-run the masking assertions (**CLAUDE.md §5.14 SC-1**), because any change to a read over `comments.body` fires that standing check.
